LEDGER — where did the money actually go?

NodeExpress Plaid APIVanilla JS

The problem

I wanted budget-vs-actual for my own money, across checking and credit cards, without paying a subscription or handing my bank credentials to someone else's cloud. The existing options were paid, hosted, or didn't let me control categorization the way I wanted. So it runs on my machine, and the data never leaves it.

What it does

  • Syncs live transactions from multiple accounts through the Plaid API
  • Monthly dashboard: income, spend, savings rate, budget-vs-actual, category breakdown
  • Re-categorize any transaction inline, and it remembers that choice permanently
  • Per-account rules that apply retroactively, with a preview before you commit them
  • Everything on disk locally — no cloud, no account, no third party

The engineering worth talking about

Transfer detection

In Plaid, a credit card payment appears twice: as money leaving checking, and as money arriving on the card. Sum those naively and you've counted a payment as both an expense and income. Every total downstream is then wrong, and it's wrong in a way that looks plausible — which is worse.

The server tags these using keyword matching (payment, autopay, ACH, transfer) alongside Plaid's own category signals. Tagged transfers stay visible in the transaction list — you should be able to see your own money moving — but they're excluded from every income and expense calculation. Most budget tools get this wrong.

Deriving the money model from groups, not categories

The version I actually use went further. Every category belongs to a group, and all the arithmetic derives from the group rather than from category IDs: 

Made  = income group
Spent = bills + variable + debt      (a loan payment is money gone)
Saved = savings group, net of inbound
Left  = Made − Spent − Saved

savings rate = Saved ÷ Made          (debt principal excluded)

Credit-card payments stay classified as transfers and stay deliberately neutral — the purchases were already counted when they were charged. Money arriving into a spending category is a refund, and reduces that category rather than counting as income. Getting these rules explicit is what made the savings-rate number trustworthy.

Debugging a UI you can't unit test

Several bugs here were invisible to unit-level checks and only showed up when the thing was actually rendered. I ended up driving the app with headless Chrome against a copy of the frontend and screenshotting the result. That caught:

  • A 100kb express.json limit silently breaking CSV export
  • A goal line painting behind its own bars
  • Date ranges ending at midnight while transactions parsed at noon — which quietly dropped the last day of every month
  • A formatter stripping the minus sign, so a savings withdrawal rendered as a deposit

That last one is the reason I don't trust a number I haven't seen rendered.

Demo mode

The portfolio build never instantiates a Plaid client unless real credentials exist. With DEMO_MODE=true the same server serves a synthetic fixture — three accounts, forty transactions, including deliberate transfer pairs so the detection logic is visible — so the whole app runs with zero setup and zero real data.

Scope

Cash flow only: checking and credit cards. Retirement and investment accounts are deliberately out — that's a net-worth problem, and mixing the two produces a number that answers neither question.

On the demo: the live version runs on my actual accounts and never gets published. A demo build on synthetic data is being prepared from the current code — the link will appear here when it's up. I'm happy to walk through the real thing on a call.
