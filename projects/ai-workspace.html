Making AI tooling something a team can actually share

Claude CodeShell hooks Team toolingDocumentation

Written up, not published. Part of this was built for a team at work, so the specifics — projects, drive layout, internal names — are left out. The pattern is transferable and it's the pattern that's mine.

The problem nobody calls a problem

Individual people were getting real value out of AI tooling. None of it was shared. Each person's setup lived on their own machine, every session started from nothing, and whatever had been worked out last week — how a dataset is shaped, why a job is run a particular way — had to be explained again from scratch.

The tooling wasn't the bottleneck. Context was. Which makes it an organizational problem wearing a technical costume.

The finding that shaped everything

Only the context file inherits by walking up the directory tree. Settings, skills, and hooks do not inherit from parent folders — they load from the folder you actually start in.

That single fact decides the whole layout, and getting it backwards is the most common way these setups quietly fail. Put a configuration at the workspace root expecting it to reach everything below and it silently does nothing, because sessions get launched from project folders. We'd had a workspace-level config directory doing exactly that — it was retired once it was clear it served no purpose.

So the structure follows the inheritance rules rather than fighting them:

workspace/
├── CLAUDE.md              inherited everywhere — shared conventions only
├── _start-here/           onboarding + a catalog of every project
├── _templates/
│   └── new-project/       CLAUDE.md · SETUP.md · config/.env.template
└── projects/
    └── <project>/
        ├── CLAUDE.md      project context, layered on the root
        ├── .claude/
        │   ├── settings.json    permissions — shared, not personal
        │   └── skills/          load only when opened HERE
        └── config/.env          credentials stay put, never synced

Agents run from their own folder, never the workspace root. That's the only place their settings and skills load.

Memory that doesn't depend on anyone remembering

The part I'd point to first. A session ends and everything worked out during it evaporates unless someone writes it down — and nobody writes it down, because the moment you'd do it is the moment you're finished and moving on.

So it's a hook, not a habit. At the end of any session, before the process is allowed to stop, it checks whether real work happened and prompts the memory files to be updated: 

read the session payload
if already handling a stop  → exit          # loop guard
if no memory store found    → exit quietly  # stay silent elsewhere
otherwise → block the stop, with a reason naming what to update

Three details make it survivable rather than annoying. The loop guard, because a hook that fires on the stop it caused never terminates. Silence where it doesn't apply, so it doesn't nag in unrelated folders. And pure Q&A sessions stop normally — if nothing changed, there's nothing to write. A tool that cries wolf gets disabled in a week.

It has to be user-level, which means it doesn't travel with the shared folder. That's a real limitation, so the fix is documentation: a setup page a new teammate follows once, written for someone who has never opened the config file before.

The unglamorous half

Most of the work wasn't the hook. It was the things that decide whether anyone else can actually use this:

  • Directional sync, never blanket overwrite. Each project was compared and moved in the direction that was actually newer. One project's live copy was already on the share and a stale local copy would have clobbered it — a one-way "sync everything" would have destroyed real work.
  • Portability. Personal config files with hardcoded local paths were removed, and the reusable permissions promoted into each project's shared settings. A config that only works on the machine it was written on isn't shared tooling.
  • A project template. A skeleton with the context file, setup notes, and a credentials template already in place, so a new project starts correct instead of starting empty.
  • A catalog. One page listing every project and what it does. Obvious, and the thing most likely to be skipped.
  • Credentials stay put. Each project holds its own local environment file, and it's never synced anywhere.

The same idea, built again cleanly

I rebuilt the pattern for my own machine afterwards, which was the useful test — the second attempt is where you find out which parts were load-bearing.

It's a different mechanism for the same function. On my own setup, recall is keyed to the directory a session starts in, while the hook that writes memory isn't keyed to anything. A hook alone would write memory everywhere and only be able to read it from one place. So it's two pieces: the hook handles writing, and a context file at the top of the home directory — the one thing that does inherit everywhere — handles reading. Same outcome, arrived at from the constraints of a different platform.

What I'd tell someone starting this

  • Find out what actually inherits before you design the folder structure. Everything else follows from it.
  • Automate the step people skip, not the step people enjoy.
  • A convention only works if a teammate can follow it without being told twice — which means the onboarding page is part of the build, not paperwork afterwards.
  • Never sync in both directions at once.

Still to add: the concrete folder structure from the team workspace, and a real outcome — onboarding time, or work that stopped being redone.
